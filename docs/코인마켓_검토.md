# 코인 마켓 검토 (가격 적정성 + 구조 재설계)

> 읽기 전용 분석(2026-11-09, design/v1 기준 data.js MYHERO 구간·myhero.js·submit-score). 가격표는 `data.js MY_ITEMS` 에서 스크립트로 추출. 수치 가정은 '가정'으로 표시, 확정 전 `tools/sim_bot.mjs mine` 으로 보정 필요.

## 요약
- 서버는 **구매·코인을 전혀 모른다**(코인·own 은 localStorage `malang-myhero2` 전용, DB 에 items/coins 컬럼 없음, scores 에는 `is_mine`·영웅 이름만). 서버가 보는 건 `validateMine`(품목 id·단계 범위·스킬 선행 조건·장착 ≤2). 따라서 '능력 2개' 규칙은 **validateMine 에 넣어야만 실제로 강제**된다.
- 가격은 **같은 효과 1단위인데 최대 7~10배 차이**가 나는 곳이 있다(예: 비상금 6.3 코인/미네랄 vs 보스 현상금 0.83 코인/미네랄). 10단계 품목(공격 훈련·영웅 근력)만 곡선이 다르고, 나머지 5단계 품목은 효과와 무관하게 40/60/95/150/230 **한 곡선을 복붙**했다.
- 코인 수급(근거: docs/내영웅_v2_스펙.md §4, 코인마켓_설계.md §8, myhero.js settle): 판당 평균 **캐주얼 58.7 / 보통 91.6**(내 영웅 판만 지급, 판당 상한 250, 하루 첫 판 +20% 최대 15 포함). 일일 상한 코드는 없음 → 하루 3판 가정 시 **캐주얼 ~176 / 보통 ~275**(가정).

## A-3. 개선 가격안 (공식) 
`가격(L) = 5 단위 반올림( 50 x V x g^(L-1) )`, V = 단계당 효과 가치(공격 +1% 모든 유닛 = 1 기준, 제안 가중치), g = 1.45(최대 6단계 이하) / 1.35(최대 10단계). 1단계 한방은 `50 x V 총가치`. 스킬은 칸·티어 고정가.
| V 가중치 | 품목 |
|---|---|
| 0.3~0.5 | 불씨 .3, 서리 .4, 되팔기 .4, 공격 훈련 .5, 보스 사냥 .5, 보스 약화 .5, 비상금 .5 |
| 0.6~0.9 | 매의 눈 .6, 공업 할인 .6, 버티기 .6, 코인 행운 .6, 속사 .8, 연금술 .8, 성장 본능 .9, 영웅 근력 .9, 사냥 보상 .9 |
| 1.0 이상 | 영웅 지휘 1.0, 끈적 발판 1.0, 보스 현상금 1.2, 꼬박꼬박 2.5, 뽑기 할인 18(총), 전리품 훈장 24(총), 공명 감각 26(총) |
기준점 = 공격 훈련 1단계 25(현행 유지). 행운 뽑기 200/320/480, 스킬 기본공격 칸 100(1단계)/200(2단계), 필살 칸 250(2단계)/400(3단계).

| 선행 조건 | 스킬 티어 1→2→3 | 칸별 | 티어 기준이라 섹션 분리 시 재정의 필요 |
| 데이터 | `MY_ITEMS` 35종 중 `sk` 있으면 스킬(11), 없으면 능력(24: 공격5·영웅2·보상3·경제5·방어4·특수5). `mine={design,items,equip:[a,b]}` | `{abilities≤2, basic, ult}` | 칸 위치가 배열 인덱스 의존(필살만 있는 상태 표현 불가: `applyMine` 이 null 을 걸러냄) |

## B-2. 요구 ① 능력 2종 제한 — 답
| 질문 | 설계 |
|---|---|
| 규칙 | 영웅당 능력 슬롯 2. 첫 구매로 슬롯이 채워지고, 2종이 차면 나머지 22종 카드는 **보이되 구매 버튼 대신 잠금 표시**. 선택한 능력은 끝 레벨까지 구매 가능 |
| 구매 불가 문구 | 카드: `🔒 능력 칸 2/2 사용 중`, 설명 한 줄: `다른 능력을 사려면 [능력 바꾸기]로 칸 하나를 비워 주세요`. 칸 상단: `내 능력 칸 [매의 눈 Lv3] [공격 훈련 Lv5]` + `바꾸기` |

| 마이그레이션 | 클라이언트(myhero.js load, `cleanHero` 확장): 능력 own 이 3종 이상이면 누적 투자액 상위 2종만 남기고 나머지 100% 환불, `note` 에 기록해 안내 모달 1회. 서버에는 이전할 데이터가 없음 |
| 서버 검증 | `validateMine`: `items` 중 `sk` 없는 키가 **3개 이상이면 거부**(`bad_mine`/`mine 능력 수 초과`). 서버는 구매·환불을 못 보므로 '2종 이내'만 강제 가능(코인 조작은 기존대로 감수) |
| DB 스키마 | **변경 없음**. 능력·코인·own 은 DB 에 없고 scores 는 hero 이름·`is_mine` 뿐. (교체 로그를 서버에서 보려면 별도 신규 마이그레이션이 필요 — 추천 안 함) |
| 환불 정책 선택지 | ①마이그레이션 환불 100%(1회), ②일반 교체 환불 50% 추천, ③교체 쿨다운(하루 1회)을 붙이면 '판 사이 메타 교체' 억제(클라 로컬이라 우회 가능, 효과 약함) |

## B-3. 요구 ② 기본공격·필살 분리 — 데이터 모델
```
mine = { design, items:{능력≤2 + 보유 스킬(=1)}, equip:{ basic:"sk_x"|null, ult:"sk_y"|null } }   // 기존 equip 배열은 [a,b] → {basic:a, ult:b} 로 읽어 변환
```
- 필드 `slot`(스킬 정의): `basic`=티어1·2, `ult`=티어2·3. 칸별 소유는 클라 `own` 키를 `sk_x@b`/`sk_x@u` 로 분리(서버 `items` 에는 스킬 id 만 보내 선행 조건 검증, 칸 검증은 `equip.basic ∈ BASIC_SET`, `equip.ult ∈ ULT_SET`).
- `applyMine`: `fx.hsk = basic`, `fx.hsk2 = ult`(null 이면 기존 규칙: 하나만 있으면 다른 칸도 같은 스킬 → **필살만 구매한 경우 기본공격은 일반 공격** 으로 바꿔야 하므로 게임 동작 변경 = 규칙 변경). game.js `defOf` 는 이미 hsk/hsk2 분리라 수정이 작음.
- `validateMine` 구형(배열) equip 도 한 버전 동안 받아들일지는 ver 검사로 불필요(아래 B-5).
