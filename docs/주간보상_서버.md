# 주간 보상 서버 (012_season_rewards.sql + submit-score rewards/rewardAck)

스펙: `docs/주간보상_스펙.md`. 파일: `supabase/migrations/012_season_rewards.sql`, `supabase/functions/submit-score/index.ts`, 테스트 `tools/test_rewards_server.mjs`.

## 구조 요약
- `reward_tbl()` 상수 한 곳(`TOP1_EXTRA` = `extra1`), `reward_base(r,k)`, `reward_bonus(r)`: 모두 immutable 순수 함수.
- 테이블 `season_rewards`(시즌·리그·기기당 1행, `total = base+bonus` 저장 계산열), `season_reward_runs`(시즌·리그당 1행 정산 완료 기록, 0명 보드도). 둘 다 RLS 켜짐·정책 없음·anon/authenticated revoke.
- `reward_settled_upto()`: (now-10분)이 속한 시즌 - 1 = 정산 가능한 마지막 시즌. 시즌 종료 후 10분 유예(제출은 요청 수신 시각에 시즌 id 를 정하고 재생 후 저장하므로 경계 직전 제출이 종료 직후 저장될 수 있어, 그 사이 정산하면 확정 순위가 바뀐다).
- `season_rewards_settle(p_season)`: 시즌 < 2 또는 > `reward_settled_upto()` 이면 0 반환(무시). 시즌별 `pg_advisory_xact_lock` 후 리그(false, true)마다: 이미 runs 가 있으면 건너뜀 -> N = `season_best_board` 행 수 -> `K = greatest(10, (3N+9)/10)` -> rank <= K 행 insert(정산 시점의 name·hero_name 도 함께 저장)(`on conflict do nothing`) -> runs insert. 한 트랜잭션이라 중간 실패 시 전부 롤백.
- `season_rewards_get(p_device)`: 미정산 시즌(2..`reward_settled_upto()`, runs < 2 행)을 오래된 순으로 정산 -> `{cur,last,pending,tbl}` jsonb 조립. `last` 는 `reward_settled_upto()` 시즌이며 두 리그 runs 중 하나라도 없으면 null(빈 보드 n:0 와 구분). top 은 `season_rewards` 의 저장값(보드 join 없음). `season_rewards_ack(p_device, int[])`: 본인 기기 미수령 행에 `claimed_at=now()`.
- 세 함수 모두 `revoke ... from public, anon, authenticated; grant ... to service_role`. 순수 함수 3개는 공개 실행 가능(읽기 전용, 무해).
- Edge Function: `rewards`/`rewardAck` 는 rate limit kind `read`(ip 40 / dev 20, profile 과 동일). `rewardAck` 입력은 `seasons` 정수 배열(1~20개, 각 1..99999, 중복 제거), 위반 시 400 `bad_seasons`. 오류 응답 형식은 기존 `{ok:false,error}`.

## 줄 단위 검산 (SQL 을 눈으로 확인, 로컬 Postgres 없음)
| 경계 | 근거(SQL 줄) | 결과 |
|---|---|---|
| N=0 | settle: `count(*)`=0 -> `k = greatest(10,(0+9)/10)=10`; insert...select 0행; runs 에 (n=0,k=10) 기록 | 보상 0행, 완료 기록 있음, 재정산 안 함. get 의 `last.leagues.*` = `{n:0,k:10,top:[]}` |
| N=5 | k=10, `rank<=10` 이 5행만 선택 | 5명 모두 보상(1위 400 … 5위 120) |
| 동점 | `season_best_board.rank` 는 `row_number() over (… score desc, played_at asc, device_id)` -> 공동 순위 없음. 정산도 `b.rank` 그대로 사용 | 운영 랭킹 화면(`leaderboard_season.rank`)과 같은 순위·같은 사람 |
| 한 기기 두 리그 | 기본키 `(season,is_mine,device_id)` -> 리그마다 1행. `get` 의 pending 은 `order by season,is_mine` -> luck 먼저 | 두 줄, 합산은 클라가 수행 |
| 재호출 | runs 존재 시 `continue`; insert 는 `on conflict do nothing` | 데이터 불변, 반환 0 |
| 동시 호출 | `pg_advisory_xact_lock(1200012,season)`; 대기한 쪽은 락 획득 후 새 문장으로 runs 확인(READ COMMITTED)이라 건너뜀; 기본키가 이중 안전장치 | 중복 행 없음 |
| 미종료/유예 시즌 | 첫 줄 `p_season > reward_settled_upto()` -> `return 0` (락도 안 잡음). get 은 `generate_series(2, upto)` 만 순회 | 진행 중이거나 종료 후 10분 이내 시즌은 정산 안 됨 |
| 시즌 1 | `p_season < 2` -> 0. get 은 2부터. `upto < 2`(시즌 2 진행 중이거나 종료 후 10분 이내)이면 `last:null` | 시즌 1 보상 없음 |
| 순위권 밖 | `b.rank <= k` 필터 | 행 없음(pending 에 안 나옴) |
| ack | `device_id=p_device and season=any(p_seasons) and claimed_at is null` | 타인 행 건드릴 수 없음, 재호출 0 |
| K 정수식 | `ceil(0.3N)=ceil(3N/10)=(3N+9)/10`(정수 나눗셈). 테스트가 N 0..5000 전수 비교 | 일치 |
| reward_base | `((200(k-1)-190(r-1)+10(k-1)-1) / (10(k-1))) * 10`, 1<=r<=k 에서 피제수 >= 0 이라 정수 나눗셈=내림이 올림 나눗셈. r=1 -> 200, r=k -> 10 | JS 참조 구현과 손계산 표 K=10/11/15 전체, 34/100/1000 지점 일치 |
| 보너스 | `reward_bonus`: 1위 b1+extra1=200, 2위 70, 3위 50 | 총액 400/250/210 |

JS 참조 구현 테스트는 SQL 식의 복사본 비교이며, SQL 문법 오류는 잡지 못한다 -> 배포 직후 아래 안전 확인 SQL 로 확인.

## 유예 10분의 클라 영향
시즌 종료(일요일 00:00 KST) 후 10분 동안은 정산도 팝업도 열리지 않는다: `rewards` 는 `last:null`, `pending:[]` 로 응답한다(직전 시즌 보상은 아직 존재하지 않음). 클라는 `last:null` 이면 `rwSeen` 을 저장하지 말고 팝업을 띄우지 않아야 하며, 다음 홈 진입(또는 10분 뒤)에 다시 조회하면 정상 팝업이 뜬다. `last` 가 있으면 항상 `last.season` 기준으로 rwSeen 을 기록한다.

## 수정본 실행 검증 (PGlite, Postgres 16 임베디드, 2026-11-10)
009 의 `season_best_board` 뷰 + 최소 `players`/`scores` + 가짜 `season_current()`/시각으로 012 수정본을 실제 실행: 37건 전부 PASS.
- 012 두 번 실행(멱등) 오류 없음. `reward_base` K=10/11/15 전체 표, K=34/100 지점 일치.
- 유예 경계(`reward_settled_upto`): 종료 5분 전 = 1, 종료 직후 5분 = 1, 정확히 10분 = 2, 직후 11분 = 2. 유예 중 settle = 0, get 은 `last:null`·`pending:[]`·runs 0행.
- 유예 후: last.season=2, luck n=12 k=10 / mine n=1 k=10, top = 400/250/210, mine top 에 hero, 한 기기 두 리그 pending 2줄, 재호출 settle=0·행 수 불변.
- S1: 정산 후 점수 레코드를 다른 시즌으로 옮겨도 top 이 정산 결과(1위 포함 3명) 유지. D2: runs 없음 + 유예 -> `last:null`. 0명 보드 시즌 2..4 정산 기록 6행, `last` 는 n:0,k:10. ack 본인만·멱등. anon 은 get 실행·테이블 select 불가.
- 한계: PGlite 는 연결 1개라 동시 호출은 실행 검증 못 함(코드 판단). 시계는 `now()` 를 가짜 시각으로 치환해 검증(헬퍼 식 자체는 동일). 검증 스크립트는 스크래치패드(저장소 밖)에 있음.

## 배포 절차
1. SQL Editor 에서 `012_season_rewards.sql` 실행(새 객체만, 재실행 안전).
2. 아래 "안전 확인 SQL" 1~2 로 함수·상수 확인. 012 끝의 `notify pgrst, 'reload schema'` 가 스키마 캐시를 갱신한다(그래도 함수가 404 면 SQL Editor 에서 이 문장을 한 번 더 실행).
3. `supabase functions deploy submit-score --no-verify-jwt` (`rewards`/`rewardAck` 포함).
4. 클라이언트 push(GAME_VER 10, sw 버전). 순서 = 마이그레이션 -> 함수 -> 클라 -> (`CONFIG.REWARDS_ENABLED`).
5. 시즌 2 는 2026-11-15(일) 00:00 KST 에 끝나고, 00:10 KST 이후 첫 `rewards` 호출이 정산한다.

## 배포 직후 안전 확인 SQL (데이터 변경 없음)
```sql
-- 1) 보상표: K=10 은 200,180,160,140,120,100,80,60,40,10
select r, public.reward_base(r,10) as base, public.reward_bonus(r) as bonus from generate_series(1,10) r;
select public.reward_base(1,34), public.reward_base(34,34), public.reward_base(500,1000), public.reward_tbl();
-- 1b) 유예 헬퍼: 지금 시각 기준 정산 가능한 마지막 시즌(시즌 2 종료 후 10분 전까지는 1)
select public.reward_settled_upto() as upto, public.season_current() as cur, now();
-- 2) 익명 차단 확인(SQL Editor 가 아니라 anon 키로 REST 호출 시 season_rewards 는 빈 배열/401 이어야 함)
select relrowsecurity from pg_class where relname in ('season_rewards','season_reward_runs'); -- t, t
-- 3) 정산 시뮬레이션(롤백으로 흔적 없음). 시즌 2 가 끝난 뒤에만 의미 있음
begin;
select public.season_rewards_settle(2);            -- 종료 후 10분 전이면 0
select public.season_rewards_settle(2);            -- 재호출: 0
select is_mine, count(*), max(total) from public.season_rewards group by 1;
select * from public.season_reward_runs;
rollback;
-- 4) 운영 랭킹과 순위 일치 확인(정산 후): 아래가 0행이어야 함
-- select r.* from public.season_rewards r join public.season_best_board b using (season,is_mine,device_id) where r.rank <> b.rank;
```
정산 시뮬은 반드시 `begin; ... rollback;` 안에서만 실행한다(실제로 정산해 버리면 되돌리려면 두 테이블의 해당 시즌 행을 delete 해야 한다; 아직 아무도 수령하지 않은 경우만 안전).

## 롤백
`012_season_rewards.sql` 맨 위 주석의 drop 목록. 새 객체뿐이므로 기존 기능 영향 없음. 함수만 되돌리면 클라는 rewards 실패를 조용히 무시. 이미 수령한 코인은 클라 로컬에 있어 서버 롤백으로 회수되지 않는다.

## 알려진 위험
- 다계정 인원 채우기: 최소 인원·계정 연결 요구가 없어 N 을 부풀려 K 를 키울 수 있다(검증된 재생 제출만 보드에 오르므로 비용은 있음). 이번엔 문서화만.
- 지연 정산: 크론이 없어 종료 후 첫 `rewards` 호출이 정산 비용(수십~수백 행 insert)을 부담한다. 종료 시각 직후 경계: 제출은 요청 수신 시각에 시즌 id 를 정하고 재생 후 저장하므로 늦게 저장될 수 있다 -> 정산을 종료 후 10분 유예(`reward_settled_upto`)로 해결. 재생이 10분 넘게 걸리는 제출은 없다고 가정.
- 시드 재사용(011 의 `on conflict (device_id, mode, seed)` 가 season·is_mine 을 덮어씀): 지난 시즌 기록이 옮겨질 수 있어 운영 랭킹 화면은 바뀔 수 있으나, 보상 팝업 top 은 정산 시점 저장값이라 정산 결과와 일치한다. 근본 수정(upsert 조건에 season 추가)은 기존 객체 변경이라 별도 승인 필요.
- 같은 device_id 를 쓰는 설치가 둘이면 ack 전에 두 번 지급될 수 있다(클라이언트 신뢰 범위)
- 동시 호출: advisory lock + 기본키로 안전하지만 대기하는 호출은 정산이 끝날 때까지 블록된다.
- 닉네임: `top` 의 name 은 현재 닉네임(변경하면 보상 화면의 이름도 바뀜). 계정이 보드에서 사라질 수는 없음(scores 삭제 시 이미 정산된 행은 남음).
- `season_best_board` 는 `players` 조인이라 players 행이 없는 기기는 보드에도 없다(정산 대상 아님).
