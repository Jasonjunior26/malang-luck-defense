# 검증: 주간 보상 서버 (012 + submit-score rewards/rewardAck)

검증일 2026-11-10, 대상: 작업 폴더 Quick-game-wr(feat/weekly-rewards) 미커밋 변경.
방법: 코드를 직접 읽음 + **PGlite(Postgres 16, 스크래치패드에 설치)에서 012 를 실제로 실행**함. 009 의 `season_best_board` 뷰 정의를 그대로 가져오고, `players`/`scores` 는 최소 스키마로, `season_current()` 는 바꿔 끼울 수 있는 가짜로 만들었다.
실행한 것: 012 를 두 번 실행(멱등), reward_base 의 기대값 표(K=10/11/15/34/100/1000, 모든 r 을 유리수 ceil 과 대조), bonus, 정산, 조회 JSON, ack, 권한(anon/service_role), 시드 재사용.
결과: 문법·타입 오류 없음. 두 번 실행해도 문제없음. base 불일치 0건. 권한도 기대한 대로다(anon 은 테이블 select·get 실행 모두 permission denied, reward_base 는 실행 가능).
동시성은 PGlite 가 연결 1개라 실행으로 확인하지 못했고, 코드를 읽어 판단했다.

## 확정 결함

### D1. [중요] 시즌 경계에 늦게 도착한 제출이 정산 뒤에 끝난 시즌 보드를 바꾼다
- 근거: index.ts 89-91행이 **요청을 받은 시각**에 `seasonInfo`(시즌 id)를 정한다. 그 뒤 재생(205행, CPU 수백 ms~수 초)과 rate limit 확인을 거쳐, 216-217행에서 `p_season: seasonInfo.id` 로 저장한다. 그래서 토요일 23:59:59 에 시작한 제출은 DB 시각이 일요일 00:00 을 넘긴 뒤에야 시즌 N 행으로 저장될 수 있다.
- 012의 75행은 `p_season >= season_current()`(DB now())만 막는다. 그래서 00:00:00.x 에 누군가 `rewards` 를 부르면 시즌 N 이 정산되고, 그 직후 늦은 제출이 시즌 N 보드에 들어간다. `submit_score_season`(011)도 지난 시즌 저장을 거부하지 않는다.
- 결과: 늦게 들어온 기록이 1위를 차지하면 운영 랭킹 화면(시즌 N 최종)의 1위와 보상 1위(400)가 달라진다. 그 뒤로는 재정산이 금지되어 고칠 수도 없다. 같은 이유로 79행 count(n→K)와 81행 insert 사이에 행이 들어오면 K 와 순위가 서로 어긋날 수도 있다. 012 5행의 "순위는 운영 랭킹 화면과 항상 같다"는 주장이 깨진다.
- 수정안(기존 객체를 바꾸지 않음): 정산과 직전 시즌 판단에 유예 시간을 둔다.
```sql
create or replace function public.reward_settled_upto() returns int   -- 정산 가능한 마지막 시즌 = (now()-10분)의 시즌 - 1
language sql stable as $$
  select case when d >= date '2026-11-08' then 2 + ((d - date '2026-11-08') / 7) else 1 end - 1
  from (select ((now() - interval '10 minutes') at time zone 'Asia/Seoul')::date as d) x
$$;
-- settle 75행: ... or p_season > public.reward_settled_upto() then return 0;
-- get 97행: generate_series(2, public.reward_settled_upto())
-- get 102-103행: last_s := public.reward_settled_upto(); (if last_s >= 2)
```
  `last` 는 "정산이 끝난 직전 시즌"을 가리켜야 한다. 그러지 않으면 유예 시간 안에 부른 클라가 n=0, top=[] 팝업을 보고 rwSeen 을 저장해 버린다(D2 참고). 클라가 `last.season` 기준으로 rwSeen 을 기록하는지 함께 확인할 것.

### D2. [중요, D1 을 고칠 때 함께] `last` 가 정산 기록 없이도 만들어진다
- 근거: 106행은 runs 행이 없으면 rn/rk 가 null 이다. 115행이 이것을 `n:0, k:10, top:[]` 로 바꿔 돌려주므로, "정산 안 됨"과 "0명 보드"를 구분할 수 없다. 지금 코드에서는 같은 호출 안에서 먼저 정산하므로 드러나지 않는다. 하지만 D1 처럼 유예를 넣거나 settle 이 0을 돌려주는 경로가 생기면 곧바로 잘못된 팝업이 뜬다.
- 수정안: 두 리그 모두 runs 행이 없으면 `last_j := null` 로 둔다.

## 의심 (근거 약함 또는 기존 결함)

### S1. [사소~중요, 기존 결함] 시드를 다시 쓰면 지난 시즌 기록이 다른 시즌·보드로 옮겨진다
- 근거: 011의 23행 `on conflict (device_id, mode, seed) do update set season = excluded.season, is_mine = excluded.is_mine` 와 index.ts 118행(시드는 클라이언트가 고름). PGlite 로 재현했다. 시즌 2의 p3 가 같은 시드로 시즌 3에 더 높은 점수를 내자, 시즌 2 보드에서 p3 가 사라지고 4위가 3위로 올라왔다.
- 영향: 정산이 끝난 뒤 지난 시즌 랭킹 화면(그리고 010 승점)이 바뀌어 보상 순위와 달라진다. 득을 보는 쪽은 본인이 아니라 다른 사람이라 악용 동기는 약하다. 우연히 시드가 같을 확률은 약 1/21억이다.
- 012 에 생기는 2차 영향: 113행이 inner join 이라, 행이 옮겨진 수상자는 `last.top` 에서 빠지고 순위에 구멍이 생긴다(예: 1위 없이 2, 3위만 표시).
- 수정안: (a) 012 에서 정산할 때 `name`, `hero_name` 을 season_rewards 에 함께 저장하고 top 은 그 값을 쓴다(join 제거). (b) 근본 수정은 별도 마이그레이션으로 upsert 키에 season·is_mine 을 넣거나 `where s.season = excluded.season` 조건을 추가하는 것이다(기존 객체 변경이므로 따로 승인 필요).

### S2. [사소] 같은 device_id 를 쓰는 설치가 두 개면 두 번 지급될 수 있다
- 지급은 로컬 코인과 로컬 `rw` 로 이루어지고, 서버 ack 는 표시만 한다. 이전 코드(import)로 같은 device_id 를 쓰는 두 설치가 둘 다 ack 전에 pending 을 받으면 양쪽 모두 지급한다. 스펙상 알려진 위험(클라이언트 신뢰) 범위다. 서버에서 막으려면 ack 를 "선점" 방식으로 바꾼다. 즉 `rewardAck` 가 새로 표시한 행만 돌려주고, 클라는 그 응답의 행만 지급한다.

### S3. [사소] security definer 의 `search_path = public`
- 72/94/130행에 pg_temp 가 명시되어 있지 않다(관계 이름은 pg_temp 를 먼저 찾는다). 참조는 모두 `public.` 으로 한정되어 있고 실행 권한도 service_role 뿐이라 실제 위험은 없다. 권장 형태는 `set search_path = public, pg_temp` 또는 `''` 이다.

### S4. [사소] 성능
- 113행의 join 과 79·81행이 `season_best_board`(전 시즌 scores 에 distinct on + window)를 매번 평가한다. 정산은 시즌·리그당 1회라 문제없다. 하지만 get 은 직전 시즌 top 을 만들 때마다 뷰를 평가하므로 데이터가 커지면 느려진다. S1(a) 처럼 이름을 저장해 두면 함께 해결된다.

### S5. [사소] 배포 직후 PostgREST 스키마 캐시
- Supabase 는 보통 DDL 이벤트로 자동 reload 한다. 012 를 실행한 뒤 함수가 404 를 내면 `notify pgrst, 'reload schema';` 를 실행한다.

## 확인한 항목 (문제없음)
- 문법·타입: plpgsql 선언, `foreach ... in array array[false,true]`, `generate_series(...) g`, `select ... into` 의 무행 null 처리, jsonb_agg 안의 `order by`, generated column, `pg_advisory_xact_lock(int,int)` 모두 실행됨. 변수(n,k,lg,done,…)와 컬럼 이름 충돌이 없다(on conflict 대상 컬럼과 같은 이름의 변수도 없음). 012 를 두 번 실행해도 됨. 기존 객체와 이름이 겹치지 않음(grep 결과 0).
- 참조: season_best_board 의 season/is_mine/device_id/name/rank(bigint→::int)/hero_name 컬럼이 009 정의와 맞다. season_current() 는 010 에 있다.
- reward_base: 모든 K(10,11,15,34,100,1000)와 모든 r 에서 유리수 ceil 과 같다. K=10 → 200,180,160,140,120,100,80,60,40,10. 범위 밖이면 0.
- K = greatest(10,(3n+9)/10) 는 ceil(0.3N) 과 같다. N=0 이면 runs 만 기록되고 보상 0건. N<10 이면 K=10 표로 1..N 위가 받는다.
- 보너스: 1=200(100+100), 2=70, 3=50 → 총액 400/250/210 실측.
- 리그 분리: 한 기기가 두 리그에 모두 들면 두 행으로 나뉘고, ack 1회로 둘 다 표시(acked=2). 동점은 played_at 이 이른 쪽이 앞선다(뷰의 row_number 그대로라 랭킹 화면과 같은 순서).
- 멱등: 같은 시즌을 다시 정산하면 0. 진행 중 시즌은 0. 시즌 1은 0(cur=2 이면 last=null). ack 를 다시 하면 0, 빈 배열이면 0, 없는 시즌이 섞여도 무시.
- 동시성(코드를 읽어 판단): 시즌별 xact advisory lock 은 get 트랜잭션이 끝날 때까지 유지된다. 기다리던 쪽은 READ COMMITTED 의 문장별 스냅샷으로 runs 를 다시 확인하므로 중복 정산이 없다. 보상 insert 와 runs insert 가 같은 트랜잭션이라 일부만 정산되는 일도 없다. 시즌을 오름차순으로 잠그므로 교착도 없다. PostgREST POST 는 읽기·쓰기 트랜잭션이고 함수는 기본값 volatile 이다.
- 권한: 두 테이블 모두 RLS 가 켜져 있고 정책이 없으며 anon/authenticated 권한은 revoke 되어 있다. settle/get/ack 는 public·anon·authenticated 에서 revoke 하고 service_role 에만 grant 했다(PGlite 실측). reward_* 순수 함수가 공개되어도 해가 없다.
- 응답: device_id 등 비공개 필드는 없다. top 은 rank/name/total(+hero) 만 담는다.
- index.ts: 'rewards'/'rewardAck' 는 `startsWith("ps")`/`startsWith("fr")` 에 걸리지 않는다. 화이트리스트에 추가되었고, device_id UUID 검증(85행)을 공통으로 거친다. 시즌 배열 검증(배열, 1~20개, 정수 1..99999, 중복 제거)은 RPC 호출 전에 끝난다. rate limit 은 read 종류. 오류는 기존 try/catch 로 처리한다. PostgREST 가 jsonb/int 스칼라를 그대로 돌려주는 형태와 응답 조립이 맞다. 다른 action 의 흐름은 바뀌지 않았다(test_rewards_server 56 PASS).
- 배포 순서: 012 만 배포되면 새 객체뿐이라 무해하다. 함수가 012 보다 먼저 배포되면 rewards 가 500 을 내고 클라가 무시한다. 클라가 먼저 배포되면 400 bad_action 이 나고 클라가 무시한다. 롤백은 drop 으로 하며, 다시 배포하면 재정산되지만 로컬 rw 덕분에 같은 설치에서는 다시 지급되지 않는다.
